# OAuth Provider Setup

This guide walks operators through configuring Google and GitHub OAuth for a
running hauth instance. After following it, users will be able to sign in with
either provider via hauth's standard OAuth 2.0 authorization-code flow.

## Overview

hauth implements the authorization-code flow. The full sequence is:

1. Your frontend redirects the user to `GET /authorize?provider=<name>&redirect_to=<url>`.
   hauth looks up the provider config, creates a short-lived flow-state record
   in Postgres (keyed by a random state token, valid for 10 minutes), and
   returns a JSON body containing the provider's authorization URL and the state
   token.
2. Your frontend redirects the browser to that authorization URL. The user
   authenticates at the provider (Google, GitHub, etc.).
3. The provider redirects back to hauth's callback endpoint:
   `GET /auth/v1/callback?code=<code>&state=<token>`.
4. hauth verifies the state token (consuming it so it cannot be reused),
   exchanges the authorization code for an access token with the provider, and
   fetches the user's identity claims (email, provider-specific user id).
5. hauth finds or creates a user record, issues a session, and returns a
   `SessionResponse` with an access token and refresh token — the same shape as
   a password login.

**State token.** The state token is a 43-character base64url-encoded random
string generated by hauth. It is stored in `auth.flow_state` and deleted
(consumed) on first use or when expired. There is no cookie involved; the
state is entirely server-side.

**Redirect allowlist.** The `redirect_to` parameter you pass to `/authorize`
must be listed verbatim in `site.allowed_redirect_urls` inside your
`config.json`. Any value not in that list is rejected with `400
invalid_redirect_to` before the flow starts.

**Redirect URI hauth registers with providers.** hauth always uses
`<site.url>/auth/v1/callback` as its `redirect_uri` when talking to the
provider. This is the URL you register in each provider's admin console —
for example `https://auth.example.com/auth/v1/callback`.

**Claims hauth pulls.** For Google, hauth fetches the OpenID Connect userinfo
endpoint (`https://openidconnect.googleapis.com/v1/userinfo`) and reads the
`sub` (stable provider user id) and `email` fields. For GitHub, hauth calls
`https://api.github.com/user` and `https://api.github.com/user/emails`,
reading the numeric `id` as the stable provider user id and the primary
verified email.


## Status and limitations

hauth's OAuth surface is deliberately narrow today. Knowing the edges up
front is cheaper than discovering them at integration time.

**Implemented:**

- Authorization-code flow start (`GET /authorize`), with a 10-minute
  single-use state token stored server-side in `auth.flow_state`.
- Code-for-token exchange against each provider's hardcoded token endpoint.
- Userinfo fetch and identity persistence into `auth.identities`.
- Session issuance returning a `SessionResponse` indistinguishable from a
  password login.
- Built-in support for two providers: `google` and `github`.

**Not implemented (deferred to v0.4 or later):**

- **OIDC discovery-document fetch.** hauth does not load
  `.well-known/openid-configuration` at startup or per-request. The
  authorization, token, and userinfo endpoints used for Google and GitHub
  are compiled into `src/Hauth/OAuth/Google.hs` and
  `src/Hauth/OAuth/Github.hs`.
- **Per-provider scope configuration.** The authorization URL hauth emits
  always carries `scope=openid email profile`, regardless of provider.
  Google honors all three; GitHub ignores them in favor of the scopes
  associated with the OAuth App. There is no config knob to change this in
  v0.2.
- **Arbitrary OIDC providers via config.** Adding a third provider
  requires the source-level steps described in "Adding new providers" at
  the bottom of this page. v0.4 plans a config-only provider type. (v0.3
  ships compiled-in modules for Microsoft, GitLab, Apple, and Discord —
  see the v0.3 milestone.)

**About the `discovery_url` field.** Despite its name, hauth does **not**
treat this URL as an OIDC discovery document to be fetched. It is the
provider's authorization endpoint base — the URL the browser is sent to
when an end user clicks "Sign in with Google/GitHub". hauth appends OAuth
query parameters (`state`, `client_id`, `redirect_uri`, `response_type`,
`scope`) to whatever you put here. The field name predates the v0.1
implementation and will be revisited alongside real OIDC discovery
support; until then, the table in the next section spells out exactly
what to paste.


## Configuring providers in `config.json`

Add each provider to the `oauth.providers` array. Each entry has four fields:

```json
{
  "oauth": {
    "providers": [
      {
        "name": "google",
        "client_id": "123456789-abc.apps.googleusercontent.com",
        "client_secret": "GOCSPX-xxxxxxxxxxxxxxxxxxxxxxxx",
        "discovery_url": "https://accounts.google.com/o/oauth2/v2/auth"
      },
      {
        "name": "github",
        "client_id": "Ov23li...",
        "client_secret": "ghp_...",
        "discovery_url": "https://github.com/login/oauth/authorize"
      }
    ]
  }
}
```

Field reference:

| Field | Required | Description |
|---|---|---|
| `name` | yes | Provider identifier. Must be `"google"` or `"github"` for the built-in providers. Case-insensitive in lookup. |
| `client_id` | yes | OAuth client/app id from the provider's developer console. |
| `client_secret` | yes | OAuth client secret from the provider's developer console. |
| `discovery_url` | yes | The provider's authorization endpoint. hauth uses this as the base URL when building the authorization redirect. For Google use `https://accounts.google.com/o/oauth2/v2/auth`; for GitHub use `https://github.com/login/oauth/authorize`. Despite the name, hauth does not fetch this URL as an OIDC discovery document — see "Status and limitations" above. |

After editing `config.json`, restart `hauth serve`. There is no hot-reload of
OAuth provider configuration in v0.2.


## Google

### 1. Create a project

Go to the [Google Cloud Console](https://console.cloud.google.com/). If you do
not have a project yet, click the project picker at the top and select "New
Project". Give it a name (e.g. "My App") and click "Create".

### 2. Configure the OAuth consent screen

In the left navigation, open "APIs & Services" > "OAuth consent screen".

- Choose "External" if users outside your Google Workspace organization will
  log in, or "Internal" for Workspace-only.
- Fill in the required fields: App name, User support email, Developer contact
  email. You can skip optional fields for now.
- Under "Scopes", add the three scopes hauth requests:
  - `openid`
  - `email`
  - `profile`
- Add any test users you need during development (while the app is in "Testing"
  publishing status, only listed users can log in).
- Click "Save and Continue" through to the Summary screen and click "Back to
  Dashboard".

### 3. Create an OAuth client ID

In the left navigation, open "APIs & Services" > "Credentials".

- Click "Create Credentials" > "OAuth client ID".
- Application type: "Web application".
- Name: anything descriptive (e.g. "hauth web").
- Under "Authorized redirect URIs", click "Add URI" and enter exactly:

  ```
  <site.url>/auth/v1/callback
  ```

  Replace `<site.url>` with the value you set in `config.json`. Example:

  ```
  https://auth.example.com/auth/v1/callback
  ```

  This URI must match exactly — scheme, host, port, and path — with no trailing
  slash. Google rejects any redirect_uri that is not in this list.

- Click "Create". A dialog shows your client ID and client secret. Copy both
  immediately; the secret cannot be retrieved again after you close the dialog.

### 4. Add to `config.json`

```json
{
  "name": "google",
  "client_id": "123456789-abc.apps.googleusercontent.com",
  "client_secret": "GOCSPX-xxxxxxxxxxxxxxxxxxxxxxxx",
  "discovery_url": "https://accounts.google.com/o/oauth2/v2/auth"
}
```

### 5. Test the flow

With `hauth serve` running:

```sh
curl -v 'http://127.0.0.1:8080/authorize?provider=google&redirect_to=http://localhost:3000/auth/callback'
```

Expected response: `200 OK` with a JSON body containing `url` and `state`.
The `url` will point to `accounts.google.com`. A `400 unsupported_provider`
means the provider block is missing or the `name` field does not match
`"google"` (check for trailing whitespace or a copy-paste quote character).

### Common errors

**`redirect_uri_mismatch`** (error shown by Google after redirect): The
`redirect_uri` hauth sent to Google does not match any URI in the "Authorized
redirect URIs" list on the credential. Check two things: (1) the URI you
registered in Google Cloud Console ends with `/auth/v1/callback`, not `/callback`
or anything else; (2) `site.url` in `config.json` is exactly the same scheme,
host, and port as what you registered (e.g., `https://auth.example.com`, not
`http://auth.example.com`).

**`invalid_client`**: The client secret is wrong. Re-copy it from Cloud
Console — a single transposed character or a trailing newline causes this.
Rotate the secret by clicking "Edit" on the credential and using "Add new
secret".

**`access_denied`**: The user cancelled, or (while the app is in "Testing"
status) the user is not in the test-users list. Add the user in the OAuth
consent screen configuration.

**Rate limits during development**: Google applies quotas per client. If you
hit them during heavy testing, create a second OAuth client ID and alternate.


## GitHub

### 1. Register an OAuth App

Go to GitHub and open "Settings" (your personal account settings, top-right
avatar) > "Developer settings" > "OAuth Apps" > "New OAuth App".

Fill in the form:

- **Application name**: anything (shown to users on the authorization screen).
- **Homepage URL**: your app's public URL.
- **Authorization callback URL**: enter exactly:

  ```
  <site.url>/auth/v1/callback
  ```

  Replace `<site.url>` with the value from `config.json`. Example:

  ```
  https://auth.example.com/auth/v1/callback
  ```

  GitHub calls this field "Authorization callback URL" rather than "redirect
  URI" but it serves the same purpose. Only one callback URL is allowed per
  OAuth App (unlike Google's list). If you need multiple environments, create
  separate OAuth Apps or use a GitHub App instead.

- Click "Register application".

### 2. Generate a client secret

On the app's settings page, click "Generate a new client secret". Copy the
secret immediately — GitHub shows it only once.

Note your "Client ID" at the top of the page (starts with `Ov` for newer apps).

### 3. Add to `config.json`

```json
{
  "name": "github",
  "client_id": "Ov23liXXXXXXXXXXXXXX",
  "client_secret": "a1b2c3d4e5f6...",
  "discovery_url": "https://github.com/login/oauth/authorize"
}
```

### 4. GitHub-specific behavior

GitHub is not an OpenID Connect provider. hauth handles this difference
internally — there is no OIDC discovery document fetch. Instead:

- hauth requests scopes `read:user` and `user:email` to obtain the user
  profile and email list.
- GitHub's `/user` endpoint may return a null `email` field for users who have
  set their email to private. hauth automatically calls `/user/emails` as a
  follow-up to find the primary verified email. If the user has no verified
  email, `identityEmail` is left null and the user record is created without an
  email address.
- The provider-level user id stored in `auth.identities` is the GitHub numeric
  user id, converted to a string.

### 5. Test the flow

With `hauth serve` running:

```sh
curl -v 'http://127.0.0.1:8080/authorize?provider=github&redirect_to=http://localhost:3000/auth/callback'
```

Expected response: `200 OK` with a JSON body containing `url` and `state`.
The `url` will point to `github.com/login/oauth/authorize`.

### Common errors

**`redirect_uri_mismatch`** (error shown by GitHub after redirect): The
callback URL you registered in GitHub's OAuth App settings does not match
`<site.url>/auth/v1/callback`. GitHub does exact-string matching. Check for
`http` vs `https`, port differences, and trailing slashes.

**`incorrect_client_credentials`**: The client secret is wrong. Rotate it in
GitHub's OAuth App settings by generating a new one.

**`bad_verification_code`**: The authorization code was already consumed or
has expired (GitHub codes are single-use and expire quickly). Restart the flow
from `/authorize`.

**No verified email**: If the user's GitHub account has no verified email,
hauth creates the user with a blank email. Downstream flows that require email
(e.g., password reset) will not work for this user until they add a verified
email on GitHub and log in again.


## Verifying with `hauth verify`

Once issue #78 lands, `hauth verify` will check that the configured provider
discovery endpoints are reachable and that the redirect URI registered with each
provider matches your `site.url`. Until then, use the `curl` smoke tests in the
provider sections above to confirm the flow start is wired correctly.


## Adding new providers

v0.2 supports Google and GitHub only. Adding a third provider requires source
changes:

1. Add a new module under `src/Hauth/OAuth/` following the patterns in
   `src/Hauth/OAuth/Google.hs` and `src/Hauth/OAuth/Github.hs`.
2. Wire it into `src/Hauth/Server/OAuth.hs` by adding a new branch in the
   callback handler's provider dispatch.

v0.4 is planned to introduce a config-only provider type for arbitrary OpenID
Connect providers, removing the need for source changes when the target is OIDC
compliant.
